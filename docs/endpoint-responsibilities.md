# `$endpoint` responsibility map

Status: maintainer architecture note.

Last verified: 2026-09-03.

This document classifies the work needed to implement Nuxt Endpoints'
`$endpoint`. It deliberately separates two meanings of "Nuxt 5 support":

- **Official stack** means the current official Nuxt, Nitro, H3, and fetchdts
  repositories.
- **Local prototype** means the `nuxt5` branch together with the matching
  `nuxt-endpoints` organization forks.

An item can therefore be absent from the official stack while already working
end to end in the local prototype. Current issue and pull-request state is
maintained separately in the [upstream tracker](./upstream-tracking.md).

## Repository boundaries

| Repository     | Responsibility for `$endpoint`                                                                                                                   | What it should not own                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| H3             | Define the route-contract grammar, infer its request and response types, and enforce the contract at runtime.                                    | Nuxt route discovery, client code generation, cache policy, or application storage.      |
| Nitro          | Extract contracts safely at build time and expose them together with the resolved route, method, and handler.                                    | A second typed-fetch schema or NE-specific client semantics.                             |
| Nuxt           | Ask the selected server builder for routes, join builder-owned type metadata to those routes, and generate one `ServerRoutes` tree.              | Interpreting H3 contract fields or status-aware result semantics.                        |
| fetchdts       | Compile and resolve the generic route/type tree, including opaque typed metadata that consumers can recover.                                     | Discovering routes, validating requests, or assigning meaning to NE's contract metadata. |
| ofetch         | Execute the HTTP request and expose raw status, body, and headers.                                                                               | Knowing Nuxt routes, server contracts, idempotency policy, or cache state.               |
| Nuxt Endpoints | Project the shared contract into the status-discriminated `$endpoint`/`useEndpoint` UX and application features such as OpenAPI and idempotency. | Reimplementing the router, server-builder inventory, or a query cache.                   |
| Pinia Colada   | Own query cache, mutation state, retry scheduling, SSR serialization, and hydration.                                                             | HTTP contract validation or server-side idempotency replay.                              |

The build-time type flow is intentionally linear:

```text
H3 contract
  -> Nitro contract extraction/provider
  -> Nuxt server:routes + builder metadata
  -> fetchdts ServerRoutes
  -> Nuxt Endpoints $endpoint types
```

At runtime, `$endpoint` uses ofetch for transport, H3 enforces the generic
contract, and NE applies its application-level policy. Pinia Colada is an
optional consumer of the same NE request object.

## Status vocabulary

The discussion column records whether the proposed ownership or behavior has
an upstream design trail:

- **Direct**: an RFC, issue, or pull request discusses this capability itself.
- **Related**: upstream work covers an adjacent primitive, but not the complete
  capability or proposed ownership boundary.
- **None**: no relevant upstream design discussion has been identified.
- **Existing API**: the capability already exists and no new design proposal is
  required for the NE integration.

The implementation columns use **Shipped**, **Partial**, and **Not shipped**
for the official stack, and **Implemented**, **Partial**, and **Not implemented**
for the local prototype.

## Upstreaming order implied by the map

1. H3 decides the generic contract shape and validation semantics.
2. Nitro exposes that contract without evaluating application handlers.
3. Nuxt accepts opaque type metadata from its server builder and joins it to
   `server:routes`.
4. fetchdts preserves that metadata without learning NE-specific semantics.
5. NE switches from fork-only integration contracts to the released upstream
   APIs and removes only compatibility adapters made redundant by those APIs.
   `$endpoint`, `useEndpoint`, OpenAPI projection, Pinia Colada integration,
   and idempotency remain.

This does not mean deleting the H3, Nitro, Nuxt, or fetchdts implementations
after upstreaming them. It means that their fork-only patches stop being
maintained separately. Inside NE, likely deletion candidates are narrow casts
and compatibility shims such as the local Nitro hook/provider type overlays;
the provider call, metadata lookup, and generated `$endpoint` types remain as
normal consumers of the upstream APIs. Platform adapters are removed only when
an upstream API covers the same measured behavior.

This order prevents a consumer-specific field from being hard-coded into
Nitro, Nuxt, or fetchdts, and prevents NE from rebuilding a route inventory
that Nuxt already owns.
