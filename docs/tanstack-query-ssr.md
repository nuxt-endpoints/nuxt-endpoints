# TanStack Query SSR Recipe

Status: both `external` and opt-in `auto` setup modes are implemented.
`external` is the default and remains e2e-tested via `test/fixtures/basic`;
`auto` is generated by `src/module.ts` and used by `playground/nuxt.config.ts`.
See
[decision 6 in the TanStack Query adapter design](./tanstack-query-adapter.md#6-ownership-of-the-nuxt-ssr-plugin).

Last consolidated: 2026-07-18

This document is a concrete, tested recipe for Nuxt SSR integration in
`external` mode: Nuxt Endpoints ships no plugin, and the application owns
`QueryClient` setup, `VueQueryPlugin` installation, and dehydrate/hydrate
transfer. It complements the design requirements in
[SSR integration](./tanstack-query-adapter.md#ssr-integration) with a runnable
implementation and its test coverage. The
[Automatic setup mode](#automatic-setup-mode) section below covers the opt-in
`auto` mode, where Nuxt Endpoints owns an equivalent generated plugin instead.

## The plugin recipe

This is the exact application plugin used by the `test/fixtures/basic` fixture
(`test/fixtures/basic/app/plugins/vue-query.ts`):

```ts
import type { DehydratedState } from '@tanstack/vue-query'
import { QueryClient, VueQueryPlugin, dehydrate, hydrate } from '@tanstack/vue-query'
import { defineNuxtPlugin, useState } from 'nuxt/app'

export default defineNuxtPlugin((nuxtApp) => {
  const vueQueryState = useState<DehydratedState | null>('vue-query', () => null)

  const queryClient = new QueryClient({
    defaultOptions: {
      queries: {
        staleTime: 60_000,
      },
    },
  })
  nuxtApp.vueApp.use(VueQueryPlugin, { queryClient })

  if (import.meta.server) {
    nuxtApp.hooks.hook('app:rendered', () => {
      vueQueryState.value = dehydrate(queryClient)
      queryClient.clear()
    })
  }

  if (import.meta.client) {
    hydrate(queryClient, vueQueryState.value)
  }
})
```

### Mapping to the nine SSR requirements

1. **Request-scoped `QueryClient` (requirement 1, 6).** `defineNuxtPlugin`
   re-runs the plugin body for every SSR request and for the one client
   bootstrap, so `new QueryClient()` here is never shared between two
   different users' requests. Do not hoist the `QueryClient` to module scope.
2. **Install `VueQueryPlugin` on both server and client (requirement 2).**
   `nuxtApp.vueApp.use(VueQueryPlugin, { queryClient })` runs unconditionally,
   so every component tree, on both sides, sees the same installed client
   during its own render.
3. **Dehydrate after render (requirement 3).** The `app:rendered` hook fires
   after Vue has finished rendering the page (and after `onServerPrefetch`
   handlers have resolved), so every query that was awaited during SSR is
   already in the cache when `dehydrate(queryClient)` runs.
4. **Transfer through Nuxt state (requirement 4).** `useState('vue-query', ...)`
   is Nuxt's existing SSR-to-client payload channel; assigning to
   `vueQueryState.value` on the server serializes the dehydrated state into the
   Nuxt payload automatically, with no separate wiring.
5. **Hydrate before client querying (requirement 5).** `hydrate(queryClient,
vueQueryState.value)` runs synchronously in the client branch of the same
   plugin, before any page component mounts and issues its first `useQuery`.
6. **No cross-request sharing (requirement 6).** Because the client is created
   inside the plugin closure per request/bootstrap and never persisted outside
   it, there is no module-level cache for two concurrent SSR requests to
   collide on. See `test/query-ssr.test.ts` for a mechanical proof and
   `isolates SSR query caches between users` in
   `test/integration/basic.test.ts` for the end-to-end proof.
7. **Cookie/authorization forwarding (requirement 7).** This part needs no
   application code: the generated `#endpoints/query` client's
   `captureFetcher` calls `useRequestFetch()` while Nuxt context is available,
   and `useRequestFetch()` forwards the incoming request's cookies and
   headers automatically. The plugin above only owns the QueryClient
   lifecycle, not the fetcher. On the server, calling
   `endpointQueryOptions`/`endpointMutationOptions`/`endpointInfiniteQueryOptions`
   factories outside Nuxt context (for example from module scope, or after an
   `await` that lost the current component/plugin/middleware instance) now
   throws a clear setup error instead of silently falling back and losing
   cookie forwarding for that request.
8. **Non-zero `staleTime` (requirement 8).** `staleTime: 60_000` is set in
   `defaultOptions.queries`. TanStack Query's own default is `0`, which is
   considered stale the instant it is set, so a freshly hydrated `useQuery`
   would immediately trigger a duplicate client-side request. This value is
   entirely an application choice in external mode; Nuxt Endpoints does not
   impose or default it. See `test/query-ssr.test.ts`'s "hydration reuse
   honoring staleTime" tests for the concrete before/after.
9. **Post-dehydration cleanup (requirement 9).** `queryClient.clear()` runs
   immediately after `dehydrate(...)` inside the same `app:rendered` hook. The
   dehydrated snapshot is a plain-object copy, so clearing the now-unneeded
   server-side cache does not affect what was already captured. See the
   "post-dehydration cleanup" test in `test/query-ssr.test.ts`.

## Page usage

Pages that need their data present in the initial server-rendered HTML use
`onServerPrefetch` together with the query's own `suspense()`:

```vue
<script setup lang="ts">
import { useQuery } from '@tanstack/vue-query'
import { onServerPrefetch } from 'vue'
import { endpointQueryOptions } from '#endpoints/query'

const query = useQuery(endpointQueryOptions.getUser({ params: { id: '123' } }))
onServerPrefetch(() => query.suspense())
</script>

<template>
  <div>{{ query.data.value?.name }}</div>
</template>
```

`onServerPrefetch` only runs during SSR; `query.suspense()` returns the same
promise `useQuery` is already tracking, so awaiting it blocks
`app:rendered` until the request settles without creating a second request.
A query that is not awaited this way during SSR render simply renders without
data on the server and fetches normally once mounted in the browser - there is
no error or extra configuration required for that case.

## Automatic setup mode

`external` (the default above) requires the application to own the plugin
recipe. Applications that do not need a custom recipe can opt into `auto`
mode instead, where Nuxt Endpoints generates and registers an equivalent
plugin itself:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-endpoints'],
  endpoints: {
    client: {
      query: {
        setup: 'auto',
        staleTime: 60_000,
      },
    },
  },
})
```

`setup: 'auto'` is opt-in; omitting `client.query.setup`, or passing
`query: true`, keeps the conservative `external` default from decision 6.
`staleTime` defaults to 60,000ms (decision 7) and only affects the generated
`auto`-mode plugin; it is meaningless in `external` mode, where the
application's own `QueryClient` owns that default.

What the module then owns is identical to the recipe above: a per-request
`QueryClient`, `VueQueryPlugin` installation, `dehydrate`/`hydrate` transfer
through a module-namespaced `useState` key (`nuxt-endpoints-vue-query`, not
the application's own `vue-query` key), and post-dehydration cache cleanup.
The generated file is written into the Nuxt build directory as
`endpoints-query-plugin.ts` (via `generateEndpointQueryPlugin` and
`addPluginTemplate` in `src/module.ts`) and registered as a Nuxt plugin, so no
application code is required.

Peer dependency behavior differs by mode. In `external` mode, an unresolvable
`@tanstack/vue-query` only produces a `logger.warn` because the application
may not use the generated `#endpoints/query` exports at all. In `auto` mode,
the generated plugin unconditionally imports `@tanstack/vue-query`, so an
unresolvable peer is a hard module setup error:

```text
[nuxt-endpoints] endpoints.client.query.setup is "auto" but "@tanstack/vue-query" could not be resolved. Install it, or use the external setup mode.
```

This throws before any other module codegen or registration runs.

Do not combine `auto` mode with an application-installed `VueQueryPlugin`
(for example, the `external`-mode recipe above, or any other manual
`nuxtApp.vueApp.use(VueQueryPlugin, ...)` call). Both would install the Vue
plugin, resulting in two independent `QueryClient` instances competing for the
same components, which silently breaks caching, dehydration, and
invalidation rather than raising an error. Choose exactly one mode per
application.

`external` remains the default and the conservative choice for applications
that already manage a `QueryClient`, need a non-default `staleTime` policy
outside of automatic mode, or want the plugin recipe visible and editable in
their own codebase.
